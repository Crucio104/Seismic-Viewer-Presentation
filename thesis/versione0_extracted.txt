Abstract
This thesis documents the design, implementation, and evaluation ofSeismic
Viewer, an advanced desktop application for four-dimensional (spatio-temporal)
visualisation and analysis of seismological datasets. The system was developed
during an internship focused on addressing a critical gap in modern seismology: the
lack of accessible, high-performance tools capable of rendering massive hypocentral
point clouds in real time while integrating spatial clustering and structural analysis.
Traditional seismic analysis relies predominantly on two-dimensional maps or
static plots that fail to capture the intricate spatial and temporal relationships
inherent in seismogenic sequences. Seismic Viewer addresses this limitation through a
hybrid architecture that combines a Python-based computational backend, leveraging
vectorised numerical computing, machine learning clustering algorithms, and robust
geospatialprocessing, withahardware-acceleratedWebGLfrontendrenderedthrough
an embedded Chromium engine.
The application supports four distinct visualisation modes: 2D geospatial map-
ping, 3D static hypocentral distribution, 4D time-animated sequences, and interactive
cluster analysis with structural plane fitting. It integrates data from diverse sources,
including local CSV files, the Italian Istituto Nazionale di Geofisica e Vulcanologia
(INGV) GOSSIP API, GNSS uplift measurements, and seismic tomography datasets.
Advanced algorithms, including auto-tuned DBSCAN and MiniBatchKMeans clus-
tering, RANSAC-based fault plane identification, and a novel global label matching
scheme for temporal stability, are employed to extract geological meaning from raw
data.
This document presents the complete software engineering lifecycle: from domain
analysis and architectural decisions through implementation details and performance
optimisations, to the resolution of significant technical challenges encountered during
development. The system has been validated using real-world datasets from the
Campi Flegrei volcanic complex, demonstrating its capability to handle datasets
exceeding 50,000 seismic events with sub-second interactive response times.

Chapter 1
Introduction
1.1 Motivation and Context
Seismology is among the most data-intensive fields within Earth sciences. Today’s
seismic monitoring networks continuously record thousands of events, generating
extensive datasets that encode critical information about subsurface processes, such
as tectonic stress accumulation and magmatic fluid migration. The capability to
interpret these vast volumes of hypocentral data in near-real time goes beyond
academic research. In fact, for regions characterized by elevated volcanic and
seismic hazards, it represents a fundamental component of risk assessment and civil
protection.
Traditionally, the analysis of earthquake catalogues has been conducted through
two-dimensional maps, cross-sections, and time-series plots. While individually
informative, these representations fail to capture the intricate four-dimensional
nature of seismogenic processes. A cluster of earthquakes migrating along a plane at
depth, for instance, may appear as a diffuse cloud in plan view yet reveal a coherent
planar structure when examined in three dimensions and animated over time. This
gap between the richness of the data and the poverty of conventional visualisation
tools motivated the development ofSeismic Viewer.
The project emerged from a direct need identified during an internship at the
Istituto Nazionale di Geofisica e Vulcanologia (INGV). Researchers studying the
Campi Flegrei caldera, one of the most densely monitored and potentially hazardous
volcanic systems in the world, required a tool that could simultaneously display
spatial distributions, temporal evolution, and structural relationships within seismic
sequences, all within a fluid, interactive environment.
1.2 Problem Statement
Despite the availability of numerous Geographic Information System (GIS) platforms
and seismological software packages, a significant technological gap persists. Existing
tools generally fall into one of two categories:
(a) General-purpose GIS platforms(e.g., QGIS, ArcGIS): These offer powerful
geospatial analysis capabilities but are not optimised for the fluid rendering of

dynamic 3D point clouds with seismic metadata. Their architectures prioritise
cartographic accuracy over real-time interactivity, resulting in prohibitive
latencies when manipulating datasets of tens of thousands of hypocentres.
(b) Specialised seismological software(e.g., Seisan, GMT, ObsPy): These pro-
vide robust analytical functionality but typically produce static outputs, such
as publication-quality figures rather than interactive explorations. The learn-
ing curve is steep, requiring command-line proficiency, and the visualisation

Neither category adequately addresses the need for a tool that unifiesreal-time
3D rendering,temporal animation,machine learning-based clustering, andstructural
geological analysiswithin a single, accessible desktop application. Seismic Viewer
was designed to fill this gap.
1.3 Objectives and Scope
The primary objectives of this project are:
1. Interactive 4D Visualisation: Develop a system capable of rendering seismic
hypocentres in three spatial dimensions plus time, with smooth animations
and real-time filtering.
2. Automated Structural Analysis: Integrate spatial clustering algorithms
(DBSCAN, K-Means) and plane fitting (RANSAC + SVD) to automatically
identify seismogenic structures.
3. Multi-Source Data Integration: Support ingestion from local CSV files,
the INGV GOSSIP online API, seismic tomography datasets (Vp/Vs ratios),
and GNSS ground deformation data.
4. Performance at Scale: Ensure sub-second interactive response times for
large datasets, through binary data transfer, GPU-accelerated rendering, and
efficient caching strategies.
5. Accessible User Experience: Provide a modern, intuitive interface that
does not require programming expertise, enabling geophysicists to focus on
interpretation rather than tool operation.
This report covers the entire development process of the application, from the
initial design to the final testing and evaluation. The system was then tested using
real earthquake data from the Campi Flegrei volcano to ensure it works well in
practice.

Chapter 2
Background and Related Work
This chapter outlines the theoretical and technical foundations of the project. It
starts by introducing fundamental seismological concepts and presenting the Campi
Flegrei volcanic complex, which serves as the primary case study for the application.
Following a review of the current state of seismic visualisation tools, the chapter
concludes by explaining and justifying the software tools selected for the development
of Seismic Viewer.
2.1 Seismological Fundamentals
2.1.1 Hypocentres and Epicentres
An earthquake is characterised by the sudden release of accumulated elastic energy
along a geological fault. The point at which rupture initiates within the Earth’s
crust is termed thehypocentre(or focus), defined by three coordinates: latitude
(ϕ), longitude (λ), and depth (z). Its vertical projection onto the surface is the
epicentre. While traditional seismological analyses often project data onto the
surface plane, losing depth information, Seismic Viewer preserves the full three-
dimensional hypocentral distribution.
2.1.2 Magnitude Scales
Earthquake size is quantified through magnitude scales. The datasets processed
by Seismic Viewer primarily use theduration magnitude(MD), which is the
standard scale employed by the INGV for local events in the Campanian volcanic
district. The system also supports generic magnitude fields (ML,M W) through its
adaptive column-matching schema (see Section 4.1).
2.1.3 Strike, Dip, and Dip Direction
The geometry of a geological is conventionally described by three parameters:
• Strike(ϕs): The compass direction of the line formed by the intersection of
the fault plane with a horizontal surface, measured clockwise from North.
--- PAGE 15 ---
2.2 The Campi Flegrei Volcanic Complex 5
• Dip( δ): The angle of maximum inclination of the fault plane relative to the
horizontal, measured perpendicular to the strike direction.
• Dip Direction: The compass direction indicating the downward inclination
of the fault plane. It is always perpendicular to the strike and is calculated as
(ϕs + 90◦) mod 360◦.
These parameters are central to the structural analysis module of Seismic Viewer,
where they are computed automatically from clustered hypocentral distributions
using the RANSAC and SVD algorithms described in Chapter 6.
2.2 The Campi Flegrei Volcanic Complex
The Campi Flegrei caldera, situated west of Naples in southern Italy, represents one
of the most significant volcanic hazard areas in Europe. The caldera, approximately
13 km in diameter, hosts a population of over 500,000 people within its boundaries
and lies adjacent to the metropolitan area of Naples.
Since 2005, the Campi Flegrei have exhibited a sustained episode of ground
uplift (bradyseism), accompanied by increasing seismicity. The INGV Osservatorio
Vesuviano continuously monitors the area through a dense network of seismic stations,
GNSS receivers, and geochemical sensors. The resulting datasets, comprising tens of
thousands of located earthquakes, daily GNSS displacement time series, and periodic
tomographic inversions, constitute the primary validation domain for Seismic Viewer.
UnderstandingthedynamicsatCampiFlegrei, suchasmagmaticfluidmovements,
hydrothermal activity, and fault reactivation, requires software that can combine
different data types in a single spatial and temporal environment. This necessity
was the main objective behind the multi-layer architecture of Seismic Viewer (see
Section 5.5). Furthermore, recent studies [3] have demonstrated that the spatial
distribution of seismicity in this caldera can be effectively modelled and represented
through planar structures, highlighting the birth and growth of volcanotectonic
faults. This finding strongly motivates and justifies the integration of specific fault
plane fitting algorithms (such as RANSAC and SVD) into the core analysis module
of the application.
2.3 Existing Seismic Visualisation Tools
QGIS and ArcGIS.While excellent for 2D cartography, their architecture is
tailored for vector and raster layers rather than dynamic 3D point clouds. Although
plugins like Qgis2threejs add 3D capabilities, performance drops when handling
thousands of features. Furthermore, creating time-based animations or clustering
data requires complex workarounds.
GMT and PyGMT.These tools are highly regarded for producing publication-
quality maps and cross-sections. However, their script-based, batch-processing
workflow lacks interactivity. Regenerating outputs after every parameter tweak
is simply too slow for the rapid, iterative exploration needed to analyse seismic
sequences.

2.4 Machine Learning in Seismology
The application of machine learning to seismological data has grown substantially
in recent years, largely supported by robust frameworks such as scikit-learn. Two
families of algorithms are particularly relevant to the spatial analysis of hypocentral
distributions:
2.4.1 Density-Based Clustering: DBSCAN
The Density-Based Spatial Clustering of Applications with Noise (DBSCAN) al-
gorithm identifies clusters as regions of high point density separated by regions of
low density. Unlike partitioning methods, DBSCAN does not require the number
of clusters to be specifieda prioriand can discover clusters of arbitrary shape, a
critical advantage when analysing seismicity aligned along non-planar fault surfaces.
--- PAGE 17 ---
2.5 Technology Choices and Justifications 7
The algorithm is governed by two parameters:ε(the neighbourhood radius) and
MinPts (the minimum number of points required to form a dense region). Points
outside these clusters are flagged asnoise, which naturally filters out scattered
background seismicity to isolate the main seismogenic structures.
2.4.2 Centroid-Based Clustering: K-Means
The K-Means algorithm partitions a set ofN observations intoK clusters, minimising
the within-cluster sum of squared distances to each cluster’s centroid. Seismic Viewer
employs theMiniBatchKMeansvariant, which processes random subsets (mini-
batches) of the data during each optimisation step. This modification reduces the
computational complexity fromO(NKT )to near-linear time, enabling real-time
reclustering as the user adjusts parameters interactively.
K-Means is preferred when the analyst has prior knowledge of the expected
number of seismogenic structures and desires spherical cluster geometries.

2.5.1 Why pywebview over Electron
To provide a smooth desktop experience without consuming excessive system re-
sources,pywebviewwas chosen over Electron. Electron is a popular framework,
but it bundles a full web browser and a Node.js runtime into the application. This
--- PAGE 18 ---
2.5 Technology Choices and Justifications 8
makes the software very heavy and demanding on memory, which is not ideal for a
tool that already requires significant resources for data processing.
Conversely, pywebview offers a much lighter solution by relying on the web engine
already installed on the user’s operating system. This ensures that the application
remains fast and uses memory efficiently.
Furthermore, pywebview includes a direct communication channel between the
user interface and the Python backend. This feature simplifies the architecture, as
standard desktop operations (such as opening files) can be handled directly, leaving
the main server free to focus entirely on transferring large amounts of seismic data.
2.5.2 Why Plotly.js over D3.js and Three.js
Rendering 3D point clouds requires a library capable of handling large datasets
efficiently. D3.js is excellent for standard two-dimensional charts, but it lacks built-in
tools for 3D environments, making it too complex for this specific use case. On the
other hand, Three.js is a powerful 3D engine, but it is too generic, implementing
scientific features like coordinate axes and color scales would require writing a large
amount of custom code.
Plotly.jsproved to be the ideal compromise. It is specifically designed for
scientific visualization and includes ready-to-use 3D components. Since it relies
on hardware acceleration (WebGL), it guarantees smooth performance even with
thousands of points. Additionally, it offers native interactive features such as zooming
and rotating, allowing the development process to focus on data analysis rather than
graphics programming.
2.5.3 Why FastAPI over Flask
The backend of Seismic Viewer needs to handle multiple tasks simultaneously, such
as serving data, maintaining active connections for real-time animations, and running
heavy clustering algorithms. Flask is a standard choice for web applications, but
its traditional architecture struggles with concurrent operations. When executing a
long calculation, Flask tends to block the entire application, causing delays in the
user interface.
To avoid these bottlenecks,FastAPIwas adopted. It is built from the ground
up to support asynchronous operations, meaning it can handle multiple requests
at the same time without freezing. This allows the system to easily offload heavy
computations to the background while smoothly transmitting the results to the user
interface through continuous data streams.

4.2 Data Sanitisation and Validation
Following ingestion, records undergo a four-stage sanitisation and validation sequence:
1. Spatial requirement check: Rows missing latitude, longitude, or timestamps
are discarded immediately.
2. Missing metadata flagging: Catalogues occasionally omit depth or mag-
nitude. Rather than dropping these records (which removes critical spatial
density) or imputing synthetic values (which biases clustering), missing fields
are flagged via boolean indicators (depth_is_missing, mag_is_missing) and
assigned sentinel defaults (0.0 km depth and magnitude 0.1).
3. Geographic and depth bounds check: The system excludes any event
with mathematically invalid geographic coordinates (i.e., latitude outside the
±90◦range or longitude outside the±180◦range). Furthermore, it discards
events with a depth falling outside the realistic geological range of−10km
to800km, where negative values are specifically permitted to accommodate
earthquakes occurring above sea level within mountains or volcanic edifices.
4. Chronological sorting & future filtering: Events with future timestamps
are discarded, and the remaining catalog is sorted chronologically to optimize
slicing.

6.1.1 Metric Space Projection
To accurately calculate distances and geometric shapes, the system cannot use raw
geographic coordinates (longitudeλand latitudeϕ) because they are measured
in spherical degrees. Furthermore, the physical distance covered by one degree
of longitude shrinks as one moves away from the equator. To solve this, before
performing any clustering, the engine converts the spherical coordinates into a flat,
3D Cartesian grid measured in kilometers(x,y,z )km. It does this by creating a
localized flat map centered exactly on the average location of the dataset(λ0,ϕ0).
This conversion, known as an equirectangular approximation, is calculated as follows:
x= (λ−λ0)·Kcos(ϕ0), y= (ϕ−ϕ0)·K, z=zdepth (6.1)
where K = 111.32km/°represents the average length of one degree of latitude,
and zdepth represents the depth of each individual earthquake (measured as positive
downwards).

6.4 Temporal Stability & Parallel Execution
During 4D animated clustering, independent per-frame executions can cause color
flickering due to non-deterministic cluster label indexing. The match_labels_
globally() routine enforces temporal stability by tracking a global label map across
consecutive frames: each cluster inherits the majority global label of its constituent
events (sampled stochastically using a maximum threshold of 200 points for large
clusters to maintainO(1)scaling with more or less99%matching accuracy).
To process multi-frame RANSAC+SVD plane evaluations efficiently, the en-
gine distributes calculations across CPU cores viaProcessPoolExecutor (capped
at min(cpu_count(), 8)). Worker processes utilize the shared memory initializer
pattern to storepts_km once at pool creation, eliminating inter-process serialization
bottlenecks across hundreds of temporal frames.

7.3 Code Quality and Architecture
The final software is organized into a clean, layered structure. The backend is
written in statically typed Python and divided into 12 distinct modules, while the
frontend is built with JavaScript, HTML, and CSS. The codebase is designed so
that data flows in a single direction: starting from the main application script
(app.py), passing through the core logic (engine.py and bridge.py), and ending
in specialized utility files (loader.py and geo_utils.py). This separation makes
the code easy to maintain and ensures that different parts of the application remain
fully independent. Finally, the system uses multiple caching strategies (on disk with
pickle, in memory withlru_cache, and for active sessions in_html_store). These
caches are kept completely separate from one another to prevent bugs where old or
incorrect data might accidentally be displayed to the user.

8.2 Validation & Performance Assessment
The system was evaluated using the dense INGV Campi Flegrei caldera catalog
(∼30,000 events, 2005-2024), characterized by intense bradyseismic swarms and
complex shallow fracturing. Quantitative profiling confirms that Seismic Viewer
achieves consistent60-120FPS rendering performance on standard desktop hardware
(M-series Apple Silicon and NVIDIA RTX GPUs) when visualizing datasets exceeding
50,000simultaneous points.
Because the true position and orientation of underground faults cannot be
directly observed, the plane fitting algorithms (RANSAC and SVD) were validated
using synthetic datasets where the exact geometric structures were known. These
datasets were generated by mathematically defining 3D planes of points at specific
strike and dip angles, and subsequently introducing random Gaussian noise and
scattered outliers to simulate realistic seismic measurement errors. These tests
demonstrated that the algorithm correctly identifies fault orientations with high
precision, consistently calculating the expected dip and strike angles even when the
data was heavily contaminated by simulated noise. Furthermore, the global label
matching algorithm (Section 6.4) successfully eliminated temporal color flickering
across 4D animated cluster sequences while maintaining fast computation times.

While Seismic Viewer achieves interactive responsiveness for current regional catalogs,

protocols (like SeedLink or FDSN web services) could transition the system

Supplementary Technical Details
This appendix provides a formal specification of the data structures and the core
algorithmic logic utilized within Seismic Viewer. Standardizing the input and internal
formats ensures that the system can easily parse external catalogs and efficiently
render them, while the computational pipeline ensures robust data analysis. By
documenting these structures and algorithms, future extensions to the software can
maintain compatibility with the existing core architecture.
A.1 Seismic Data Structures
The design of Seismic Viewer places a strong emphasis on maintaining a clear
separation between the external data representation and the internal state used
for high-performance computation. This section outlines both formats in detail,
illustrating how raw textual data is efficiently translated into numerical matrices.
A.1.1 Input Catalog Format
Seismological data must be structured in a CSV following the specifications de-
tailed in table A.1. The schema requires specific temporal and spatial fields to
ensure correct localization within the 3D WebGL environment. To accommodate
the vast amount of data often recorded during seismic swarms, the format is kept as
lightweight as possible. External catalogs, such as those provided by the INGV, must
be pre-processed or mapped to this standard structure before ingestion. The manda-
tory fields include unique identifiers, precise origin timestamps, and geographical
coordinates expressed in decimal degrees.
A.1.2 Internal Application State
Once parsed by the Python backend, the catalog is transformed into an internal state
object optimized for rendering and clustering algorithms. The data is held in memory
as multi-dimensional numpy arrays to facilitate the matrix operations required by
DBSCAN and RANSAC. Transitioning from a row-based CSV structure to a column-
based array format significantly improves memory locality and cache performance
during heavy numerical computations. This design choice is fundamental to achieve
the interactive frame rates needed in the application’s GUI.

A.2 Algorithmic Pipeline
The objective of the spatial analysis module is to extract dominant structural
orientations from unorganized point clouds representing earthquake hypocenters.
This is achieved through a multi-stage pipeline that first isolates dense clusters
of seismicity and then determines the geometric properties of the underlying fault
structures.
A.2.1 Spatial Clustering
The system employs DBSCAN to group seismic events that occur in close spatial
proximity, effectively separating them from isolated, background seismicity. The
clustering logic evaluates distances in three dimensions using a Euclidean metric,
allowing it to identify arbitrarily shaped clusters without requiring the user to specify
the number of groups beforehand. The core implementation relies on the highly
optimizedscikit-learnlibrary to process tens of thousands of points efficiently.
A.2.2 Fault Plane Extraction
For each identified spatial cluster, the system estimates the best-fitting geometric
plane. This process relies on the RANSAC algorithm to iteratively sample subsets of
the cluster and discard outliers that do not conform to a planar structure. Once the
set of robust inliers is identified, SVD is applied to the centered coordinates. The
normal vector of the fault plane corresponds to the right singular vector associated
with the smallest singular value, providing a mathematically rigorous definition of
the structure’s orientation in 3D space.
