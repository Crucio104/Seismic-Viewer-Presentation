Abstract
This thesis documents the design, implementation, and evaluation ofSeismic
Viewer, a desktop application for four-dimensional (spatial and temporal) visual-
isation and analysis of seismological data. The system was developed during an
internship to address a limitation in existing tools: the lack of software capable
of rendering large hypocentral point clouds in real time while integrating spatial
clustering and structural analysis.
Traditional seismic analysis often relies on two-dimensional maps or static plots
that do not show the spatial and temporal evolution of earthquake sequences. Seismic
Viewer addresses this limitation through a dual architecture that combines a Python
computational backend (using vectorised numerical computing, clustering algorithms,
and geospatial processing) with a hardware-accelerated WebGL frontend rendered
through an embedded web engine.
The application supports four visualisation modes: 2D geospatial mapping, 3D
static hypocentral distribution, 4D time-animated sequences, and interactive clus-
ter analysis with structural plane fitting. It integrates data from local CSV files,
the INGV GOSSIP online API, GNSS vertical ground deformation, and seismic
tomography datasets. Analytical algorithms, including auto-tuned DBSCAN, Mini-
BatchKMeans clustering, RANSAC plane fitting, and a label matching method for
temporal consistency, are used to identify geological structures in the data.
This thesis presents the development process from requirements and system archi-
tecture to implementation, testing, and performance optimization. The application
was evaluated using earthquake data from the Campi Flegrei caldera, showing that
it can render and analyze datasets with more than 50,000 seismic events in real time.

Chapter 1
Introduction
1.1 Motivation and Context
Seismology is a data-intensive domain within Earth sciences. Seismic monitoring
networks continuously record events, generating datasets that describe subsurface
processes such as tectonic stress accumulation and magmatic fluid migration. Inter-
preting hypocentral data in near-real time is important for volcanic and seismic risk
assessment.
Traditionally, earthquake catalogues have been analyzed through two-dimensional
maps, cross-sections, and time-series plots. These representations do not fully capture
the four-dimensional spatial and temporal distribution of seismic processes. An
earthquake sequence migrating along a fault at depth may appear as a diffuse group
in map view, but reveal a planar structure when examined in three dimensions and
animated over time. This limitation of conventional visualisation tools motivated
the development ofSeismic Viewer.
The project was developed during an internship at the Istituto Nazionale di
Geofisica e Vulcanologia (INGV). Researchers studying the Campi Flegrei caldera
required a tool to display spatial distributions, temporal evolution, and structural
relationships within seismic sequences in an interactive desktop application.
1.2 Problem Statement
Despite the availability of numerous Geographic Information System (GIS) platforms
and seismological software packages, a significant technological gap persists. Existing
tools generally fall into one of two categories:
(a) General-purpose GIS platforms(e.g., QGIS, ArcGIS): These offer geospa-
tial analysis capabilities but are not designed for rendering dynamic 3D point
clouds with seismic metadata in real time. Their architectures prioritize carto-
graphic precision over interactivity, leading to delays when handling datasets
with tens of thousands of hypocentres. From a software architecture perspec-
tive, traditional GIS tools often use synchronous data processing and standard
text formats like JSON. When handling large datasets with tens of thousands
of points, this causes the user interface to freeze due to high memory usage
and parsing delays.
--- PAGE 11 ---
1.3 Objectives and Scope 2
(b) Specialised seismological software(e.g., Seisan, GMT, ObsPy): These
provide robust analytical functionality but typically produce static outputs,
such as static figures for print rather than interactive explorations. The learn-
ing curve is steep, requiring command-line proficiency, and the visualisation
paradigm remains fundamentally two-dimensional.
Neither category adequately addresses the need for a tool that unifiesreal-time
3D rendering,temporal animation,machine learning-based clustering, andstructural
geological analysiswithin a single, accessible desktop application. Seismic Viewer
was designed to fill this gap.
1.3 Objectives and Scope
The primary objectives of this project are:
1. Interactive 4D Visualisation: Develop a system capable of rendering seismic
hypocentres in three spatial dimensions plus time, with smooth animations
and real-time filtering.
2. Automated Structural Analysis: Integrate spatial clustering algorithms
(DBSCAN, K-Means) and plane fitting (RANSAC + SVD) to automatically
identify seismogenic structures. In particular, solve the cluster label switching
issue across consecutive 4D animation frames to keep colors consistent over
time.
3. Multi-Source Data Integration: Support ingestion from local CSV files,
the INGV GOSSIP online API, seismic tomography datasets (Vp/Vs ratios),
and GNSS ground deformation data.
4. Performance at Scale: Ensure sub-second interactive response times for
large datasets, through a custom Float32 binary streaming protocol, an asyn-
chronous multi-channel communication design (native bridge, HTTP REST,
WebSockets), GPU-accelerated rendering, and efficient caching strategies.
5. Accessible User Experience: Provide a modern, intuitive interface that
does not require programming expertise, enabling geophysicists to focus on
interpretation rather than tool operation.
This report covers the development process of the application, from the initial
design to testing and evaluation. The system was evaluated using earthquake data
from the Campi Flegrei caldera. In addition to practical usability, this thesis explains
the software engineering solutions used to connect Python scientific calculations with
interactive 3D web graphics. The following chapters present the domain background,
the system architecture, the data processing pipeline, the visualisation modes, the
algorithmic foundations, the development process, and the conclusions drawn from
this work.

Background and Related Work
This chapter outlines the theoretical and technical foundations of the project. It
starts by introducing fundamental seismological concepts and presenting the Campi
Flegrei volcanic complex, which serves as the primary case study for the application.
Following a review of the current state of seismic visualisation tools, the chapter

2.1 Seismological Fundamentals
This section introduces the basic seismological concepts needed to understand the
data and analysis in Seismic Viewer.
Hypocentres and Epicentres.When an earthquake occurs, energy is released
underground along a fracture. The exact point inside the Earth where the rupture
begins is called thehypocentre(or focus). It is defined by three coordinates:
latitude (ϕ), longitude (λ), and depth (z). The point directly above the hypocentre
on the surface of the Earth is theepicentre. Traditional maps often show only the
epicentre on a flat surface, losing the depth information. Seismic Viewer preserves
the full three-dimensional position of each hypocentre to show the true underground
structure.
MagnitudeScales.Themagnitudemeasurestheenergyreleasedbyanearthquake.
In local monitoring catalogues, such as those for the Campanian volcanic area,
the INGV primarily uses theduration magnitude(MD). Seismic Viewer can
automatically detect and load different magnitude types (MD, ML, MW) during
data import (see Section 4.1).
Fault Geometry: Strike, Dip, and Dip Direction.Earthquakes often occur
along underground fracture surfaces called faults, which can be represented geo-
metrically as tilted planes. To describe the orientation of a fault plane in three
dimensions, geologists use three fundamental angles:
Thestrike( ϕs) is the compass direction of the fault line. It is defined as
the orientation of a horizontal line lying on the tilted plane, measured in degrees
--- PAGE 15 ---

clockwise from North (0◦≤ϕs < 360◦). By convention, when looking along the
strike direction, the fault plane slopes downward to the right.
Thedip( δ) is the steepness or inclination of the fault plane. It is the angle
between the tilted plane and a horizontal surface, measured along the line of
maximum slope perpendicular to the strike. The dip angle ranges from0◦for a
completely horizontal plane to90◦for a vertical fault.
Thedip directionis the compass direction toward which the fault plane slopes
downward into the subsurface. It is always perpendicular to the strike (at a 90-degree
angle to the right):
Dip Direction= (ϕs + 90◦) mod 360◦ (2.1)
Together, strike and dip define the complete 3D position of a geological fault. In
Seismic Viewer, these angles are calculated automatically from earthquake clusters
by fitting planes using the RANSAC [4] and SVD [17] algorithms (described in
Chapter 6).
2.2 The Campi Flegrei Volcanic Complex
The Campi Flegrei caldera, situated west of Naples in southern Italy, is an active
volcanic area in Europe. The caldera, approximately 13 km in diameter, hosts a
population of over 500,000 people within its boundaries and lies adjacent to the
metropolitan area of Naples.
Since 2005, Campi Flegrei has experienced ground uplift (bradyseism) accompa-
nied by seismic swarms [2]. The INGV Osservatorio Vesuviano monitors the area
through seismic stations, GNSS receivers, and geochemical sensors. The resulting
datasets, comprising thousands of located earthquakes, daily GNSS displacement
time series, and tomographic inversions, form the primary validation domain for
Seismic Viewer.
Analyzing subsurface processes at Campi Flegrei, including fluid movement and
fault activation, requires integrating multiple data sources within a shared spatial
and temporal framework. This requirement motivated the multi-layer architecture
of Seismic Viewer (see Section 5.5). Furthermore, recent studies [5] showed that
earthquake hypocentres in this caldera can be approximated by planar surfaces,
supporting the integration of plane fitting methods (RANSAC and SVD) into the
application.
2.3 Existing Seismic Visualisation Tools
The software landscape for seismological data visualisation encompasses Geographic
Information Systems (GIS), script-based mapping utilities, domain-specific Python
libraries, observatory processing suites, and general-purpose 3D visualisation software.
Understanding the strengths and limitations of these tools clarifies the specific gap
filled by Seismic Viewer.
--- PAGE 16 ---
2.3 Existing Seismic Visualisation Tools 7
QGISandArcGIS.Thesegeneral-purposeGISplatformsexcelat2Dcartography,
spatial overlay analysis, and integrating seismic events with surface infrastructure
and geological maps. However, their core architecture is designed for 2D raster and
vector layers rather than dense, dynamic 3D point clouds. Although 3D views can
be rendered natively or via plugins like Qgis2threejs, performance drops significantly
when handling tens of thousands of hypocentres. Furthermore, they lack built-in
tools for interactive 4D time-windowed playback and automated structural fault
plane fitting.
GMT and PyGMT.The Generic Mapping Tools (GMT) and its Python interface
(PyGMT) represent the standard choice for producing high-resolution static maps,
cross-sections, and focal mechanism plots. However, GMT is fundamentally a batch-
processing, script-driven tool that generates static image files (such as PostScript or
PNG). It does not provide an interactive graphical environment where an analyst
can rotate 3D scenes in real time, interactively adjust clustering parameters, or
observe dynamic earthquake migrations.
ObsPy.ObsPy is the standard open-source Python framework for seismological
research, offering comprehensive tools for waveform processing, event metadata
management, and standard file format support (such as MiniSEED, SAC, and
QuakeML). While ObsPy is indispensable for data ingestion and signal processing,
it is a programming library rather than an interactive end-user application. Its
visualisation capabilities rely mainly on static 2D Matplotlib figures.
Seisan.Seisan is a widely used software suite for earthquake observatory workflows,
including phase picking, hypocentre location, and seismic database management.
While reliable for routine monitoring, its user interface and codebase are based on
legacy terminal utilities and Fortran routines, presenting a steep learning curve and
lacking modern, hardware-accelerated 3D/4D visual exploration capabilities.
ParaView.ParaView is a powerful open-source scientific visualisation engine
based on VTK, capable of rendering massive 3D and 4D volumetric datasets, such as
seismic tomography models and wave propagation simulations. However, ParaView
is a general-purpose scientific visualisation tool: it requires complex data pipeline
configurations and lacks domain-specific seismological features, such as direct online
catalog ingestion (e.g., the INGV GOSSIP API), automated hypocentral clustering,
and strike/dip fault plane extraction.
GPlates.GPlates is an interactive plate tectonics tool designed for reconstructing
geological continental motions across global scales and deep geological time (millions
of years). While it supports 3D spheres and time animation, it is designed for global
plate kinematic models rather than high-resolution, local earthquake sequences or
real-time volcano-seismic monitoring.

2.4 Machine Learning in Seismology
The application of machine learning to seismological data has grown substantially in
recent years, building on established pattern recognition and clustering foundations
[8] and supported by libraries such as scikit-learn [12]. Two families of algorithms
are particularly relevant to the spatial analysis of hypocentral distributions, and
Seismic Viewer integrates both to offer complementary analytical perspectives.
Density-Based Clustering: DBSCAN.The Density-Based Spatial Clustering
of Applications with Noise (DBSCAN) algorithm [3] identifies clusters as regions of
high point density separated by regions of low density. Unlike partitioning methods,
DBSCAN does not require specifying the number of clustersa prioriand can identify
structures of arbitrary shape, which is useful when analysing non-planar fault zones.
The algorithm uses two parameters:ε(the neighbourhood radius) andMinPts (the
minimum number of points required to form a dense region). Points outside these
clusters are marked asnoise, filtering out background seismicity to isolate structural
features. Implementation details and parameter tuning strategies are discussed in
Chapter 6.
Centroid-Based Clustering: K-Means.The K-Means algorithm [9] partitions a
set ofN observations intoK clusters by minimising the within-cluster sum of squared
distances to each cluster centroid. Seismic Viewer uses theMiniBatchKMeans
variant, which processes random subsets (mini-batches) of data at each step. This

2.5.1 Architectural Trade-Off: pywebview vs. Electron
Selecting the desktop framework affects memory usage and execution speed. While
Electron[ 10] is widely used for desktop web apps, it bundles a Chromium browser
and Node.js with the application. This configuration uses 150–250 MB of RAM in
idle and requires inter-process communication between Node.js and Python.
In contrast,pywebview[ 18] uses the web component present in the operating
system (WebView2 on Windows, WebKit on macOS). This keeps idle memory usage
under 40 MB and avoids bundling an extra browser runtime. In addition, pywebview
provides a direct JavaScript–Python bridge (js_api), allowing UI actions and native
file dialogs to execute without network overhead.
2.5.2 Rendering Engine Selection: Plotly.js vs. Low-Level Graphics
APIs
Rendering 3D earthquake datasets interactively requires GPU acceleration via
WebGL.Low-levelgraphicsengineslikeThree.jsprovidecontrolovervisualelements,
but require implementing 3D axes, projections, legends, and camera controls from
scratch. Conversely, 2D charting tools likeD3.jslack 3D WebGL support.
Plotly.js[ 13] combines WebGL acceleration with built-in scientific plotting
features and interactive controls. By using Plotly’s WebGL pipeline and preserving
the camera state during updates (uirevision), Seismic Viewer achieves 60 FPS
rendering for over 50,000 earthquakes without requiring a custom graphics engine.
2.5.3 Backend Server Framework: FastAPI vs. Traditional WSGI
The backend streams binary data buffers and handles WebSocket messages (progress
updates, parameterfilters)alongsidemathematicalcalculations. SynchronousPython
web frameworks likeFlaskorDjangocan block incoming requests during long
calculations unless coupled with external task queues.
FastAPI[14], based on the Starlette ASGI framework and theuvicorn[1] server,
uses an asynchronous event loop viaasyncio. This design supports WebSocket com-
munication and HTTP endpoints within a single process. Numerical calculations are
offloadedtobackgroundthreadsorprocesspoolsusing asyncio.run_coroutine_threadsafe,
keeping the user interface responsive.

3.2.2 Session Store & FastAPI Middleware
The system architecture requires a dedicated memory management layer to pre-

frontend. This functionality is centralized within an internal configuration module

tridimensional scenes instantaneously. Both structures implement a First-In, First-

updates to these stores are synchronized, maintaining application RAM usage below
500 MB during extended sessions.
Positioned between this caching layer and the client interface, the FastAPI server
deploys specific middleware to optimize network throughput. The most critical
optimization is the automatic application of GZip compression for any outgoing
data payload larger than 500 bytes. Compressing the data prior to transmission
significantly accelerates the rendering process, particularly when transferring datasets
containing tens of thousands of seismic events.

Following ingestion, records undergo a four-stage sanitisation and validation sequence:
1. Spatial requirement check: Rows missing latitude, longitude, or timestamps

2. Missing metadata flagging: Catalogues occasionally omit depth or magni-
tude. In seismic analysis, estimating missing depths (such as using the mean
value) is avoided because it groups points into artificial horizontal layers, dis-
torting clustering and plane fitting results. Rather than dropping these records
(which removes spatial density) or imputing synthetic values, missing fields
are flagged via boolean indicators (depth_is_missing, mag_is_missing) and
assigned sentinel defaults (0.0 km depth and magnitude 0.1).
3. Geographic and depth bounds check: The system excludes any event
with mathematically invalid geographic coordinates (i.e., latitude outside the
±90◦range or longitude outside the±180◦range). Furthermore, it discards
events with a depth falling outside the realistic geological range of−10km
to800km, where negative values are specifically permitted to accommodate
earthquakes occurring above sea level within mountains or volcanic edifices.
4. Chronological sorting & future filtering: Events with future timestamps
are discarded, and the remaining catalog is sorted chronologically to optimize
slicing.

4.5 Pre-computation and Memory Layout Transforma-
tion
To ensure the 3D map remains fluid and responsive even with thousands of earth-
quakes, the software performs several calculations in advance (during the data
loading phase) rather than while the user is interacting with the map. The
precompute_visual_data() function handles two main tasks. First, it pre-renders
tooltip strings in a single batch operation, so that the browser does not need to
construct the text for pop-ups every time the mouse hovers over an event. Second, it
converts calendar dates into normalised time metrics (days since the first earthquake),
accelerating chronological color mapping.
The data pipeline converts raw CSV lines into contiguous NumPy numerical
arrays (numpy.ndarray). This enables vectorised operations on coordinates, depths,
and timestamps. To stream data to the client efficiently, arrays are converted to 32-
bit floating-point values (np.float32) and transmitted as raw bytes viatobytes(),
avoiding JSON encoding overhead.
Embedding large amounts of earthquake data directly into an HTML file increases
file size and causes the browser to lag. To prevent this, Seismic Viewer uses an
asynchronous loading strategy. When the user requests a 3D view, the backend
generates an HTML page containing the 3D environment, base terrain maps, and UI
menus. Once the base map is displayed, the browser requests the earthquake points
in the background via/api/data/{id}/bin. These points are delivered as a Float32
binary buffer and populated onto the map without blocking user interaction.

refined results can subsequently be applied back to merge cleanly into the parent

7.3 Code Quality and Architecture
The software is organised into a modular structure. The backend is written in
Python with type annotations across 12 modules, while the frontend is built with
JavaScript, HTML, and CSS. Data flows unidirectionally: from the application entry
point (app.py), through the bridge and engine (bridge.py, engine.py), to utility
modules (loader.py,geo_utils.py).
A key aspect of the architectural design is the strict isolation of caching strategies.
The system uses multiple caching layers operating at different levels: persistent disk
caching with pickle for map tiles and terrain meshes, in-memory function-level
caching with lru_cache for frequently accessed computations, and session-scoped
stores (_data_store and _html_store) for active analytical workspaces. Keeping
these caches separate prevents data inconsistency.
This modular organisation was not the original design. As discussed in Section 7.1,
the codebase underwent two major refactoring cycles during the internship. The
first split a single monolithic script into separate modules organised by responsibility,
while the second introduced the FastAPI and WebSocket infrastructure to replace
the original synchronous communication model. These refactoring efforts, though
time-consuming, were essential for maintaining code quality as the application grew
in complexity.

8.1 Summary of Contributions
The analysis of existing seismic visualisation tools presented in Section 2.3 revealed
a persistent gap in the available software landscape: no single application combined
interactive 3D rendering, temporal animation, automated clustering, and structural
geological analysis within an accessible desktop environment. Seismic Viewer was
designed to fill precisely this gap. The contributions of this project can be grouped
into three main areas: software architecture, data visualisation, and automated
analysis.
From an architectural perspective, the most significant contribution is the dual-
engine design that separates computation from presentation (Chapter 3). By coupling
a pywebview [18] native window with a high-throughput FastAPI [14] local server,
the application achieves full desktop integration (native file dialogs, window man-
agement) without the memory overhead that a framework such as Electron [10]
would impose. This separation is important because it allows the scientific Python
backend to perform heavy numerical operations independently from the user inter-
face, preventing the graphical environment from freezing during long calculations. A
second architectural contribution is the custom binary streaming protocol, which
packs numerical arrays into contiguous Float32 buffers and reduces the data transfer
volume by approximately90%compared to traditional JSON serialisation. This im-
provement was essential for achieving fluid interactivity, as the original JSON-based
approach caused the browser engine to freeze for several hundred milliseconds when
parsing large catalogues.
In the area of data visualisation, Seismic Viewer introduces a multi-modal
rendering system comprising four complementary views: 2D geospatial maps, 3D
static hypocentral distributions, 4D time-animated sequences, and interactive cluster
analysis workspaces. The 4D animation mode, in particular, represents a novel
contribution for desktop seismological tools. It allows researchers to observe how
earthquake sequences evolve over time through three distinct temporal windowing
strategies (accumulation, sliding window, and block mode), providing insights into
migration patterns and the progressive activation of fault segments that would
remain invisible in static representations. Additionally, the integration of auxiliary
geophysical layers (seismic tomography cubes, GNSS vertical displacement grids,
--- PAGE 50 ---
8.2 Validation and Quantitative Performance Assessment 41
and monitoring station positions) enables researchers to correlate seismicity with
deeper crustal processes within a single coherent spatial environment.
The third area of contribution concerns the automated structural analysis pipeline.
Seismic Viewer implements three complementary clustering approaches, DBSCAN [3],
MiniBatchKMeans [9], and a custom cylinder grid partitioning method, each suited
to different analytical scenarios. The cylinder partitioning strategy, in particular,
was developed specifically for this application to ensure stable cluster assignments
during 4D temporal animations without the colour swapping that affects standard
unsupervised algorithms across independent frames. On top of these clustering
methods, the application automatically fits structural fault planes using a two-stage
RANSAC [4] and SVD [17] pipeline, directly computing geologically meaningful
parameters such as dip, dip direction, and strike. This combination of clustering
and plane fitting within an interactive, real-time environment allows researchers
to identify and characterise seismogenic structures without resorting to external
analytical software.

The system was evaluated using the dense INGV Campi Flegrei caldera catalogue,

service, eliminating the need for local installation.
A second important direction concerns real-time monitoring integration. The
current architecture analyses static or periodically updated catalogues, but integrat-
ing continuous data streaming protocols such as SeedLink or FDSN web services
could transform the system into a live surveillance dashboard suitable for monitoring
rooms. This would require extending the WebSocket communication layer to handle
continuous data ingestion alongside the existing analytical pipeline.
Finally, future iterations could expand the analytical capabilities by integrating
focal mechanism visualisations to represent fault kinematics directly in the 3D scene,
as well as Coulomb static stress transfer maps to analyse how individual earthquakes
redistribute tectonic stress across neighbouring faults.
8.4 Concluding Remarks
Seismic Viewer demonstrates combining web technologies with Python libraries
for geophysical analysis. The hybrid architecture separating the Python backend
from the WebGL frontend balanced computation speed with development workflow.
Python libraries (NumPy [6], scikit-learn [12]) provide numerical routines, while the
web frontend delivers GPU-accelerated 3D graphics.
The iterative methodology aligned software capabilities with research require-
ments. Feedback from domain experts at INGV Osservatorio Vesuviano and Roma
Tre University guided features such as sub-clustering and cylinder partitioning.
This work supports the transition from static plots toward interactive exploration
in seismology. By providing 4D visualization and clustering in a desktop application,
Seismic Viewer offers a foundation for studying seismogenic structures and monitoring
volcanic unrest at Campi Flegrei [2, 5].
